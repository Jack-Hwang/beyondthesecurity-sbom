## 2. SLO (수식과 근거)

### 2.1 서빙 지연 (console API)

- **SLO: API p95 ≤ 100 ms** (조작: 콘솔 JSON 읽기 경로).
- 근거 수식: `headroom = SLO / p95_측정값`, 경로별로 따로 잡는다 (2026-11-22 07:56 3경로 실측):
  - `/healthz` (검사 없음): 100 / 23.89 ≈ **4.2배** — 프로세스 생존 신호일 뿐, SLO 근거로는 가장 약하다.
  - `/readyz` (검사 수행: 폴더 쓰기+import+코퍼스): 100 / 23.52 ≈ **4.3배** — 검사 비용이 p50에서
    측정 불가능할 수준(2.01 vs 2.03 ms)이라는 것이 이번 실측의 발견이다.
  - `/api/history` (증거 폴더 읽기): 100 / 60.67 ≈ **1.6배** — **가장 빠듯한 경로**. 히스토리 행 수가
    늘어날수록 이 수치가 나빠지므로, SLO 여유의 지배 항은 파일 읽기다. 히스토리가 수십 건을 넘길 때
    다시 재고, 여유가 1배에 접근하면 페이지네이션(행 제한)이 다음 구현항이 된다.
- 남은 한계(정직): 위 세 경로 외의 `/api/*`(스캔 제출, LLM 채팅, SSE)는 여전히 **미측정**이다. 채팅
  스트림은 이벤트별로 흩어져 단일 지연 수치가 의미가 없고(스트림 완료 시간이 지표), 스캔은 2.2의
  처리량 식이 지배한다.
- LLM 경로(EXAONE/Azure 왕복 1~3초)는 이 SLO에서 **제외**한다 — 외부 왕복은 용량 산정 대상이 아니라
  가용성 대상이고, 프로젝트는 이미 LLMUnavailable·회로 차단기로 그 실패를 격리한다.

### 2.2 스캔 처리량

- 단일 프로세스는 스캔을 병렬로 돌리지 않는다(ThreadingHTTPServer의 요청 스레드와 무관하게 파이프라인 자체가
  순차). 따라서 처리량 상한은 시간당 완주 수:
  `λ_max[스캔/시] = 3600 / W` — W는 스캔 1건 평균 소요.
- 이 저장소(6,298 컴포넌트) 실측: W = 31.7 s(파이프라인) → `λ_max ≈ 113 스캔/시`;
  오프라인 라이선스 갭을 포함한 단계 전체 W = 104.31 s → `λ_max ≈ 34 스캔/시`.
  **보수치로 34/시를 쓴다** — 온라인 레지스트리 왕복은(W↑) 오프라인보다 빠르지 않다는 근거가 없기 때문.
- 크기 스케일링(추정, 수식): 스캔 시간이 컴포넌트 수에 대략 선형이라면 `W ≈ 104 s × (N/6298)`
  (N = 대상 저장소 컴포넌트 수). 선형성 자체는 미검증 — 두 번째 크기 레벨을 측정하면 갱신.

### 2.3 동시성 (Little's Law)

- `L = λ × W`: 큐에 머무는(진행 중) 스캔 수 = 도착률 × 소요시간. 서버는 job을 스레드로 받으므로
  도착이 몰리면 스캔이 **동시에** 돌아 메모리가 먼저 한계가 된다(스캔 1건 = 원본 work copy + 결과).
- 제안 상한(추정): 스캔 1건이 대상 저장소 크기 수준의 디스크·메모리를 쓰므로
  `동시 상한 ≈ 사용 가능 메모리 / (저장소 크기 × 복사 계수 ≈ 2)`. 이 저장소 기준 실측치(스캔 중 RSS)는
  **미측정** — 측정 없이 상수를 채우지 않는다.
- 실용 규칙(실측 근거 없음, 설계 근거): 로컬 단일 사용자 도구이므로 동시 스캔은 1건으로 제한하는 것이
  예측 가능하다. `/api/scan`은 이미 job 큐(`st.jobs`)로 받지만 동시 실행 자체를 막지 않는다.

### 2.4 가용성

- SLO 후보: 월 가용 99%(월 7.2h 중단 예산). 단일 프로세스·단일 노드에서 이것은 "프로세스가 떠 있다"의
  합이다 — 실제 가용 측정 인프라(업타임 모니터)는 없으므로 **목표 선언만 있고 실측 없음**. 런북의
  `/readyz` 3연속 503 롤백 트리거가 이 수의 유일한 수호 장치다.

## 3. 스케일 축 (4-2차시 KEDA/HPA가 아닌 것)

과정의 HPA/KEDA/CA는 복제 단위가 필요하다. 이 제품의 스케일 축은:
`프로세스 1개 × evidence 볼륨 1개`를 한 단위로, **프로세스를 추가하고 볼륨을 분리**하는 것(수직→수평 전환
지점). 서비스가 무인증이라 프로세스를 늘리는 순간 리버스 프록시와 인증이 전제가 되고, 그 시점에 런북과
이 문서는 재작성 대상이다(패치 아님).
