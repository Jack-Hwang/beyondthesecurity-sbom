# 심화과정 5~6주차 교안 -> BTS-SBOM 구현 매핑 (정직 판)

1~2주차는 `docs/METANET_ADVANCED_MAPPING.md`, 3~4주차 이전 기법은 `docs/LECTURE_MAPPING.md` 에 있다. 이 문서는 5주차(4차시)와 6주차(2차시), 모두 6개
교안을 읽고 **이 앱에 실제로 비어 있던 구멍**만 골라 구현한 기록이다. "구현"은 테스트와 측정값이 있는 것만 뜻한다 (BSA-AC-1000~1088, 46개).

## 1. 읽은 교안

| 차시 | 주제 | 이 앱에 닿는 핵심 |
|---|---|---|
| 5주차 1차시 | Prompt Flow 에이전트 | 플로·평가 흐름·회귀 평가, 에스컬레이션·모호성 해소 규칙(다중 매칭 시 되묻기), 승인 요청 4요소, 조용한 실패를 잡는 게이트 |
| 5주차 2차시 | Fine-tuning + RAG 고도화 | "할 수 있다"보다 "해야 하는가", 홀드아웃 구성표, 세그먼트별 정확도 |
| 5주차 3차시 | ML 파이프라인 ① 구성·자동화 | 재현성 = 무엇을 버전으로 고정했는가, 보류셋 버전 고정, 버전으로 고정한 프롬프트 |
| 5주차 4차시 | ML 파이프라인 ② 배포·모니터링·거버넌스 | 드리프트·비용·안전성 모니터링, 롤백, 감사 |
| 6주차 1차시 | 멀티 에이전트 최종 아키텍처 | 1~5주차 통합, 승인 요청(HITL), 리뷰에서 방어 |
| 6주차 2차시 | 프로젝트 설계·진행 | 비중첩 병렬 구현, 게이트, DEV 배포 |

## 2. 추론한 구멍과 구현

이 코드베이스는 이미 크다(회귀 게이트·케이스 회귀·인용 검증·HITL 승인 토큰·Azure 배포 등). 그래서 교안의 항목을 하나씩 "있다/없다"로 대조해
**실제로 없던 것**만 만들었다.

| 교안 개념 | 이미 있던 것 | 실측으로 확인한 구멍 | 만든 것 | AC |
|---|---|---|---|---|
| 조용한 실패를 잡는 게이트 | 코어의 `data_status`/`vulnerability_presence` 의미: `complete`+`none` 만 검증된 "깨끗함" | 오프라인/미조회/미지원 매니페스트로 부분 스캔인데도 챗이 "취약점이 없다"고 답함 | `gaps.py`: 기록의 한계를 코드가 갭으로 만들고 모든 챗 답변·fleet 질의·분석 보고에 공시. 부분 스캔에서 못 찾음 = "검증 안 됨" | 1000~1010 |
| 에스컬레이션 (D5.2) | `handoff.error_envelope`, 대화 메모리, HITL 승인 토큰 | 챗에 "사람에게 넘기는" 경로가 없고 같은 실패를 반복 | `escalation.py`: 사람 요청 / 정책 공백(법적 판단·보증) / 무진전(연속 3회 미응답) 세 트리거를 **코드가** 결정 (감정·자신도 점수 아님). 구조화 페이로드, 추가 전용 `escalations.jsonl`, 해결 메모의 환류, API·CLI | 1020~1026, 1029~1031 |
| 모호성 해소 (다중 매칭 시 되묻기) | `_pick_project` 가 휴리스틱으로 하나를 고름 | 같은 컴포넌트/CVE 가 여러 프로젝트에 있어도 하나를 추측해 답함 | 프로젝트를 안 밝힌 모호 질문은 후보를 들어 되묻고 도구를 돌리지 않음 | 1027 |
| 승인 요청 4요소 | 승인 토큰·확인 코드 | 미리보기에 무엇이 승인되는지만 있고 "승인 안 하면"·기한이 없음 | 패치 계획·VEX 결정 미리보기에 결정 / 승인 시 / 미승인 시 / 기한 | 1028 |
| 세그먼트별 평가 (5-2) | 총합 지표 + 케이스 회귀 | 총점이 평평한데 한 주제가 나빠지는 변화(순위 1→2 와 2→1 상쇄)를 못 잡음 | `rag.evaluate` 가 세그먼트(주제·언어·범위 밖)별 recall/MRR, 루프 게이트가 세그먼트 하락(>0.10)을 총점 불변이어도 차단 | 1060~1063 |
| 보류셋 버전 고정 (5-3) | `code_fingerprint`(코드+평가 파일 전체 해시) | 평가셋이 바뀐 줄 모르고 옛 베이스라인과 비교 가능 | 평가셋별 내용 지문 핀: 다른 버전이면 **비교 무효(undecidable)**. 의도적 재기준선은 사유 필수, 평가셋이 안 바뀌었으면 거부(회귀 세탁 불가) | 1064~1067, 1072 |
| 평가셋 유출·구성 점검 (5-2 홀드아웃 구성표) | rag_test 는 "튜닝 전에 작성" 이라는 약속만 | 약속을 검증하는 코드가 없음 | `evalguard.leak_check`: 홀드아웃이 튜닝 세트와 중복·근접 중복(문자 3-gram Jaccard ≥ 0.8)이거나 코퍼스에 복사됐거나 닿을 수 없는 기대 출처면 차단. 구성표(크기·범위 밖 비율·세그먼트·얇은 세그먼트·없는 언어) | 1068~1071, 1073 |
| 버전으로 고정한 프롬프트 (5-3) | `ai.PROMPT_VERSION`(캐시 키) | 프롬프트가 10여 곳에 흩어져 있고 council 의 캐시 키는 시스템 프롬프트를 안 넣음 | `promptreg.py`: 소스를 AST 로 읽어 상수 8개 + 인라인 7개(15개)에 지문을 매기고 `evals/prompt_registry.json` 에 핀. 드리프트·미등록·삭제·**버전 미상향** 이면 검사 실패, 재핀은 사유 필수. 루프 패스는 프롬프트 digest 를 기록하고 바뀌면 교란 경고 | 1080~1088 |

## 3. 실측 (2026-11-26)

- **RAG 지표는 그대로**: golden recall 1.0 / MRR 0.95 / OOD 1.0, dev 1.0 / 0.836 / 1.0, test 0.917 / 0.75 / 1.0 (세그먼트 필드만 추가, 기존 `evalrag` 변화 없음).
- **홀드아웃(rag_test)은 깨끗함**: 튜닝 세트와의 중복·근접 중복 0건, 코퍼스 복사 0건, 닿을 수 없는 기대 0건. 차단 발견 0건.
- 발견 1건(경고): `rag_dev` 의 질의 하나(`고쳤는데 새 문제가 더 생기면 원상복구 하나`)가 지식 노트에 그대로 들어 있다. dev 는 튜닝에 쓴 세트라 차단은 아니지만
  이 질의의 점수는 낙관적이다.
- **구성 편향**: 세 평가셋 모두 in-domain 질의가 전부 한국어다(영어 0건). 영어 질문에 대한 검색 품질은 **측정된 적이 없다**.
  세그먼트가 n<2 로 얇은 곳도 많다(rag_test 는 5개 주제). 얇은 세그먼트는 보고만 하고 게이트하지 않는다.
- **프롬프트 15개**가 핀으로 고정됐다. 코드 수정 없이 다시 계산해도 digest 가 같다(`d4b64f1a53b9`).
- 신규 테스트 46개 (갭 11, 에스컬레이션 12, 평가셋 무결성 14, 프롬프트 레지스트리 9).

## 4. 하지 않은 것과 이유

| 항목 | 상태 | 이유 |
|---|---|---|
| 파인튜닝 | **미구현(의도)** | 교안 기준(지식 vs 형식)으로 이 앱의 결핍은 지식이고 RAG 가 푼다. 학습 데이터·홀드아웃·비용 근거가 없으면 "해야 하는가"의 답은 아니오다. |
| Azure ML / Prompt Flow 서비스 종속 | **미구현(의도)** | 이 앱은 표준 라이브러리 전용·오프라인 우선이다. 플로 "개념"(평가 흐름·회귀·버전 고정)만 가져왔다. |
| Batches API | 미구현 | 호출 주체가 EXAONE 일일 한도(장부)이고 대량 비동기 작업이 병목이 아니다. |

## 5. 운영 규칙 (바뀐 작업 절차)

- 프롬프트를 고치면 `bts-sbom-app prompts` 가 실패한다. 평가를 돌린 뒤 `bts-sbom-app prompts --update --reason "<무엇을 왜>"`. 그 모듈에 `PROMPT_VERSION` 이 있으면
  **먼저 올려야** 재핀된다(캐시된 모델 출력이 새 문구에 재사용되는 것을 막는다).
- 평가셋을 고치면 다음 `ragloop` 패스가 undecidable 이다. 의도한 변경이면 `bts-sbom-app ragloop --variable ... --rebaseline "<무엇을 왜>"`. 평가셋이 그대로인데
  지표만 떨어졌다면 재기준선은 거부된다.
- `bts-sbom-app evalsets` 는 구성표·지문·유출 점검을 보여 주고 차단 발견이 있으면 종료 코드 1이다.
- 챗이 넘긴 건은 `bts-sbom-app escalations` / `GET /api/escalations` 로 보고, `--resolve ID --note ... --by ...` 로 닫는다. 닫은 메모는 그 프로젝트의 이후 답변 끝에
  **데이터로** 붙고 검증된 주장으로 취급되지 않는다.

## 6. 한계

- 에스컬레이션 트리거 문구는 한국어·영어 정규식이다. 목록 밖의 표현은 못 잡는다(무진전 트리거가 마지막 안전망). 거짓 양성 방지 테스트(승인 토큰·확인 코드·화난 말투 단독)는 있다.
- 세그먼트 게이트는 n≥2 만 본다. 평가셋이 작아서(25/20/16개) 세그먼트 하락 허용치를 0.10 으로 넓혔고, 개별 질의 손실은 기존 케이스 회귀 게이트가 정확히 잡는다.
- 프롬프트 지문은 템플릿 소스의 지문이다. 템플릿에 끼워 넣는 값(예: 액션 목록)이 코드에서 바뀌면 변경 리뷰로 잡아야 하고 지문에는 반영되지 않는다.
- 핀 파일(`evals/prompt_registry.json`)은 같은 작업 트리에서 다른 세션이 프롬프트를 고치면 그 세션의 테스트를 실패시킨다. 의도된 동작이다(재핀 절차 안내가 실패 메시지에 있다).
