# ISO/SAE TR 8477:2026 검토와 SBOM / 오픈소스 스캐닝 추가 기능

- 작성일: 2026-11-20
- 대상: ISO/SAE TR 8477:2026 (1st edition, 2026-11) "Road vehicles - Cybersecurity verification and validation"
- 상태: **검토 제안서 (코드 변경 없음)**. 구현할 묶음을 고르면 그때 스펙(EARS)과 테스트를 붙여 만든다.

## 1. 먼저 밝힐 한계

- 읽은 파일은 **비공식 "readability edition"** 이다. 원본 34쪽(Part I)에 OCR 층과 다시 조판한 도면 라벨이 섞여 있고, 파일 스스로 "라벨은 편집상 복원이며 출판사 원본과 대조하지 않았다"고 밝힌다.
  본문(1~8절, 부속서 A)은 PyMuPDF 텍스트 추출로 읽혔고 도면 라벨만 불확실하다. 아래 조항 번호와 인쇄 쪽수는 이 파일 기준이다.
- 이 문서는 **방법을 규정하지 않는 기술 보고서**다("focuses on strategy and does not prescribe methods"). SBOM 형식, 필드, 오픈소스 스캐너 요건은 **없다.**
  SBOM 이라는 말은 본문에 두 곳(5.2 계획 예시, 6.7)뿐이고, 방법의 세부는 SAE J3322:2025 로 넘긴다. J3322 와 ISO/SAE 21434 본문은 보지 못했다.
- 따라서 아래 "추가 기능"은 TR 8477 이 **요구한 것**이 아니라, 이 문서의 V&V 틀(전략, 근거 보고, 재사용, 변경 영향, 가정, 독립 평가)을 SBOM·스캐닝 도구에 옮기면 무엇이 비는지에서 **추론한 것**이다.
- 저작권 때문에 본문을 옮기지 않고 요약했다.

## 2. 문서의 골격 (내 말로)

| 절 | 내용 |
|---|---|
| 4 | 검증(V)은 요구사항 계층 어디에나, 타당성 확인(V)은 최상위(목표, 개념 요구사항, 가정, 주장)에 적용. 아키텍처 계층마다 가능. 가정은 문서화하고 V&V 대상. TARA 가 기대는 속성은 실제 구현되었는지 확인. 구성요소 재사용, 맥락 밖 개발, 기성품(COTS)별로 근거가 부족하면 어떻게 메울지 |
| 5 | V&V 전략(범위, 방법과 선택 근거, 신뢰 절차)과 계획(활동, 책임, 일정, 시작/종료/반복 기준, 합격/불합격 기준, "shift left" 우선순위, 고객-공급자 분담, 자동화 관리) |
| 6 | 방법군: 리뷰, 분석, 형식기법, 코드 분석(소스/바이너리), 기능 시험(긍정/부정), **취약점 스캐닝**, 퍼징, 스트레스, 결함 주입, 침투 시험, 암호 시험 |
| 7 | 방법을 TARA, 가정, 목표, 개념, 요구사항·설계에 적용하는 예(표 1~5) |
| 8 | V&V 보고: 추적성, 범위, 결과와 발견, 계획 대비 편차, 결론 + 검증/타당성 보고서 발췌 예(표 6~8) |
| A | V&V 는 증거를 만들고, **사이버보안 평가는 그 증거를 독립적으로 판단**한다("four eyes") |

## 3. SBOM / 오픈소스와 닿는 대목 (조항별)

1. **5.2 계획 예시(인쇄 12쪽)**: BOM 을 입력으로 받고, BOM 에서 알려진 취약점을 식별하고, 취약점 스캔을 하고, 결과를 식별된 취약점과 교차 확인하고, 개념증명(PoC) 공격으로 시험한다. 순서가 곧 파이프라인이다.
2. **6.7 취약점 스캐닝(15쪽)**: 같은 또는 유사한 항목에서 확인된 취약점이 대상에 남아 있지 않은지 확인하는 방법군. 도구는 CVE 나 국가 DB 를 조회하고 CVSS 심각도와 조치 제안을 낸다.
   **SCA 가 SBOM 을 만들고, 그것을 취약점 DB 와 교차 조회**하는 것을 자동화 예로 든다.
3. **6.11 침투 시험(17쪽)**: 취약점의 **존재**(a)와 **악용 가능성 입증**(b)을 구분한다. 존재만 확인하는 것은 이 문서가 시험으로 치지 않는 "취약점 평가"다.
4. **6.5 코드 분석(14쪽)**: 바이너리 분석은 이름·타입 정보가 사라져 소스 분석보다 정보가 적다.
5. **4.9 재사용 / 맥락 밖 / 기성품(10~11쪽)**: ISO/SAE 21434 로 만들지 않은 레거시나 상용 기성 구성요소는 V&V 근거가 부족할 수 있다.
   설계를 볼 수 없으면 블랙박스 시험, **그 구성요소나 유사 구성요소의 사이버보안 모니터링 결과로 근거 대체**, 구성 점검으로 메운다. 변경이 있으면 회귀 분석이나 회귀 시험을 추가한다.
   기성품은 개발 인터페이스 합의가 없어도 출시 후(모니터링) 합의는 의미가 있다.
6. **4.7 작업 산출물 갱신(8쪽)**: 인수인계 시점에 산출물의 **동결된 기준선**이 있고, 인계 뒤 한쪽이 발견한 것이 상대에게 영향을 줄 수 있다. 발견, 구성요소 변경, 정제가 갱신을 일으킨다.
7. **4.8 가정(9쪽)**: 모든 산출물은 가정에 기댈 수 있고, 가정은 명시하며 검증/타당성 확인 대상이다. 환경에 대한 가정은 타당성 확인한다.
8. **8.1 보고(21~22쪽)**: 보고서는 대상 식별, 전략/계획/요구사항/시험 명세(버전)/시험 환경 참조, 범위(통합 계층, 화이트/그레이/블랙박스, 합격 기준, **제외와 이유**), 결과(전체 pass / pass with restrictions / fail, 항목별, **공격 실현 가능성 평가의 입력**, 조치 제안), 계획 대비 편차, 결론을 담는다.
9. **표 3~5(20~21쪽)**: 가장 흔한 CWE 에 대한 리뷰를 근거 방법으로 든다.

## 4. 현재 BTS-SBOM 과의 대응

| TR 8477 의 요소 | 지금 있는 것 | 비어 있는 것 |
|---|---|---|
| BOM 입력 -> 알려진 취약점 -> 스캔 -> 교차 확인 | SBOM 파일을 소스로 스캔(코어가 읽음), 소스 분석, OSV 조회 | **교차 확인**: 공급자 SBOM 과 실제 산출물(소스/바이너리)의 대조가 없음 |
| 6.7 취약점 스캐닝, CVSS, 조치 제안 | OSV 스캔, CVSS v3/v4, 검증된 업그레이드 계획, 승인형 패치 | 같은 약점 유형의 재발(유사 항목) 관점 없음 |
| 6.11 존재 vs 악용 입증 | 도달성은 코어(C/C++)에만, 기본은 UNKNOWN | 발견의 **증거 수준**(존재/정적 도달성/입증됨)이 레코드에 없음 |
| 6.5 바이너리 분석의 한계 | `binscan`: 문자열 증거만, 식별은 안 함(스스로 명시) | 한계는 문서화돼 있으나 SBOM 대조에 쓰지 않음 |
| 4.9 COTS/재사용 근거 부족 | 라이선스, EOL, 변경 감시(직전 1건) | 구성요소별 **근거 충분성 평가**, 모니터링 이력(직전 1건만 보관) |
| 4.7 기준선, 인계 후 발견 | `diff`(직전 대 현재), `.prev.json` | **동결된 기준선**과 "인계 후 새 권고" 구분 |
| 4.8 가정 | triage 의 justification, expires, by | 가정과 그 **검증 근거 참조**가 없음 |
| 8.1 보고 형식 | 프로젝트 보고서, 산업 리포트, 결정 커버리지 그래프(`coverage.py`) | **V&V 보고서 형식**(추적성, 범위, 제외 이유, 결과 등급, 편차, 결론) |
| 표 3~5 CWE 리뷰 | 없음(권고의 CWE 를 읽지 않음) | CWE 집계와 체크리스트 씨앗 |
| 부속서 A 독립 평가 | 결정에 `by` 만 있음 | 작성자와 다른 **검토자 확인** 상태 |

## 5. 추가 기능 검토

각 항목: 무엇을, TR 근거, 기존 모듈에서 어떻게, 정직성 규칙, 규모(S/M/L). 모두 결정적이고 읽기 전용이며, LLM 은 설명만 쓰고 계산된 사실에 없는 수치는 버린다는 이 저장소의 규칙을 그대로 따른다.

### P1 - V&V 증거 보고서 + 공격 실현 가능성 입력 + CWE + 증거 묶음 (한 묶음, M)

- **A. V&V 보고서(`vnv-report`)**: 분석 한 건을 TR 8.1 형식으로 낸다. 추적성(대상 구성요소와 커밋, 사용자가 준 계획/요구사항 참조 `--plan-ref --req-ref`, 도구와 코어 버전, DB 조회 시각, 온라인/오프라인),
  범위(통합 계층, 접근 = 소스 SCA 는 화이트박스, 바이너리 문자열은 블랙박스, 합격 기준 = 정책, **제외와 이유**: 못 읽은 파일, 조회하지 못한 패키지, 지원하지 않는 매니페스트),
  결과(pass / pass with restrictions / fail 과 항목별), 조치 제안(업그레이드 계획), 계획 대비 편차, 결론. 마크다운 + JSON, `/api/vnv/<project>`.
  - 정직성: 오프라인이거나 조회하지 못한 패키지가 있거나 존재만 확인했으면 **pass 가 아니라 pass with restrictions**. "악용 가능성은 시험하지 않았다"를 범위에 고정 문구로 넣는다(6.11).
- **G. 공격 실현 가능성 입력**: v3/v4 벡터의 지표(AV, AC, AT, PR, UI)를 항목별로 풀어 `attack_inputs` 로 싣는다. **입력일 뿐 등급이 아니다**(등급은 TARA 의 몫이라 만들지 않는다).
- **E. CWE 집계**: OSV 권고의 CWE 목록을 레코드에 싣고(`database_specific.cwe_ids`), 프로젝트와 포트폴리오(`fleet`)에서 상위 CWE 를 낸다. 표 3~5 의 "가장 흔한 CWE 대비 리뷰" 체크리스트의 씨앗이고, 6.7 의 "유사 항목 재발" 관점의 첫걸음이다.
- **H. 증거 묶음(`bundle`)**: SBOM, VEX, 레코드, 보고서의 SHA-256 목록과 도구 버전, 시각을 담은 매니페스트. 평가자가 무엇을 받았는지 고정한다. 서명은 키가 있을 때만(이번 범위 밖).

### P2 - 공급망 신뢰 (각 S~M)

- **B. SBOM 대 산출물 대조(`reconcile`)**: 공급자가 준 SBOM 을 소스 매니페스트와 락파일, 바이너리 문자열 증거와 대조한다. 결과는 선언되지 않은 구성요소(후보), 산출물에서 못 찾은 구성요소, 버전 불일치,
  BOM 기준 취약점과 스캔 기준 취약점의 차이. 5.2 의 "교차 확인"을 구현하는 것이다.
  - 정직성: `binscan` 문자열은 **식별이 아니라 증거**이므로 "선언되지 않은 것으로 보인다(후보)"까지만 말하고, 없다는 것을 단정하지 않는다.
- **C. 동결 기준선과 인계 후 발견**: 인계 시점의 SBOM + 발견 + VEX 를 내용 해시로 동결하고(`freeze`), 이후 분석에서 기준선 구성요소에 새로 붙은 권고를 "인계 후 발견(상대 당사자에게 영향)"으로 표시한다. 4.7 의 기준선과 인계 후 발견에 대응하며 `changes.py` 위에 얹는다.
- **D. 가정 등록부**: `inline_mitigations_already_exist`, `vulnerable_code_cannot_be_controlled_by_adversary` 로 `not_affected` 를 주려면 **가정 문장과 검증 근거 참조**가 필요하고, 없으면 `affected` 로 남아 사유에 "가정 미검증"을 적는다(fail-closed 확장). 4.8 에 대응.

### P3 - 이후 (M~L)

- **F. 재사용/COTS 근거 충분성**: 구성요소별로 "있는 근거"(SBOM, 스캔, 라이선스, EOL, 권고 이력)와 "빈 근거"를 표로 내고 4.9.2 의 대체 근거(블랙박스 시험 제안, 모니터링 이력, 구성 점검)를 제안. 유지보수 신호는 네트워크 메타데이터가 필요해 오프라인 부분부터.
- **I. 방법군 커버리지와 외부 증거 가져오기**: 6절 방법군 중 도구가 한 것(SCA, 바이너리 문자열, 소스 라이선스)과 안 한 것(퍼징, 정적 보안 분석, 침투)을 보고서에 드러내고, SARIF(코어에 `sarif.py` 있음)와 퍼징 충돌 요약, 침투 시험 발견을 가져와 같은 보고서에 묶는다.
- **J. 검토자 확인(four eyes)**: 심각도 높은 `not_affected` 는 작성자와 다른 `reviewed_by` 가 있어야 "확정", 아니면 "검토 대기"로 내보낸다(부속서 A).
- **K. 모니터링 이력**: 지금 직전 1건만 남기는 `.prev.json` 대신 분석 시각 이력을 보관해, 출시 후 모니터링의 증거(4.9.4)로 쓴다.

## 6. 하지 않을 것

- **조항별 적합 판정**: ISO/SAE 21434 이행 여부는 평가자의 독립 판단(부속서 A)이다. 도구는 증거를 모으고 빠진 곳을 보여줄 뿐 "적합"을 내지 않는다.
- **공격 실현 가능성 등급 산출, TARA 대체**.
- **존재 확인을 악용 입증처럼 표시**: 증거 수준 구분(존재 / 정적 도달성 / 입증됨)을 지키고, 입증은 사람이 남긴 것만 인정한다.
- 근거 없는 pass: 조회하지 못했거나 오프라인이면 항상 제한 있는 결과.

## 7. 추천 순서

1. **P1 묶음(A + G + E + H)**: 가장 작은 변경으로 "스캔 결과"가 평가자가 읽는 "V&V 증거"가 된다. 기존 레코드만으로 계산되고 새 네트워크 의존이 없다.
2. **B**: 공급자 SBOM 을 믿지 않고 확인하는 기능이라 자동차 공급망에서 가장 쓸모가 크고, 이 문서의 5.2 가 직접 요구하는 순서다.
3. **C, D**: 기존 `changes.py`, `triage.py` 의 확장이라 작다.
4. P3 는 수요를 보고.

## 8. 물어볼 것

- 대상이 자동차 부품 공급자 워크플로(고객-공급자 합의)인가, 아니면 일반 SBOM 도구에 이 형식을 선택 항목으로 넣는 것인가? 전자라면 `--plan-ref`, 사이버보안 인터페이스 합의(CIA) 참조 필드를 1급으로 둔다.
- SAE J3322:2025 와 ISO/SAE 21434 본문을 볼 수 있나? 6.7 의 SCA 세부(J3322 17.92, 17.2)가 거기 있어 보고서 필드를 더 정확히 맞출 수 있다.
