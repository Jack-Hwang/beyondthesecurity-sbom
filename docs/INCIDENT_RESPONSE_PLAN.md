# 침해사고 대응 RFP 분석 → BTS-SBOM 기능 제안 (2026-11-28)

원문: KISA 「27년 침해사고 원인분석 및 대응조치 지원 용역 제안요청서」(3,200백만원·12개월·20명 상주).
본 문서는 RFP의 요구를 우리 SBOM 공급망 보안 서비스에 접목할 **기능 제안**으로 변환한다. 원칙은 기존과
같다: RFP의 문장을 그대로 기능으로 옮기되, 우리 제품이 이미 갖춘 계약(HITL·SLA·정직 보고·근거 인용) 위에 얹는다.

## 1. RFP → 기능 매핑 (제안)

## 2. 구현 범위 (루프 방식, 3루프 병렬 배치)

- **루프 1 (AC-1261)**: `incidents.py` — 사고 레코드·상태기계(전진 전용)·SLA 시계·지연사유·만족도·
  롤업 + `GET/POST /api/incidents…` (host pinning·same-origin·입력 한도 검증). 저장은
  `evidence/incidents/<id>.json` (oss_api와 같은 evidence 폴더 관례).
- **루프 2 (AC-1262)**: 보고서 생성기 4종 — 초동/원인분석/증거수집 체크리스트/대응방안 모음집.
  빈 필드는 "미확인"으로 채워지고 절대 지어내지 않는다(4상태 철학).
- **루프 3 (AC-1263)**: IoC 등록·공급망 교차조회 + 챗 도구 `ioc_impact`(읽기 전용) + dock 다음 단계
  매핑 + 레일 "🚨 사고 대응" 섹션·판.

## 3. 의도적 제외 (정직 기록)

- 증거데이터 실수집(디스크 이미지·메모리 덤프 수집 도구)은 침해대응 현장 영역 — 우리는 SaaS 분석 제품이므로
  체크리스트와 관리만 제공하고 수집 자체는 제안하지 않는다.
- 정보공유 세미나(연2회)·보안교육 실시는 사람 운영 업무 — 제품 기능이 아니라 운영 절차.
- 1영업일 SLA의 "영업일" 계산은 1차 근사로 달력일을 쓴다(법정휴일 달력은 후속 과제로 명시).
