# AI 고도화 제안: Karpathy 저장소에서 BTS-SBOM(취약점 스캔 · 라이선스 검출)으로

- 작성일: 2026-11-17 / 상태: **제안서 (코드 변경 없음)**
- 조사 대상: https://github.com/karpathy?tab=repositories (63개 중 60개 목록 확인. autoresearch · llm-council · rendergit · hn-time-capsule · reader3 · nanochat · jobs 7개는 README 수준까지 확인,
  arxiv-sanity-lite는 목록의 한 줄 설명만 보고 판단)
- 조사의 한계(먼저 읽으세요): 저장소 내용은 WebFetch 요약본으로 읽었고 **소스 코드는 직접 읽지 않았습니다**. 아래 "차용"은 메커니즘(아이디어)이며 코드를 가져오는 안이 아닙니다.
  코드를 가져올 경우 각 저장소의 LICENSE를 따로 확인해야 합니다(이번에 확인한 것은 rendergit=BSD0, reader3=MIT 뿐입니다).
  또 Karpathy 본인이 대부분을 "vibe coded / 유지보수 안 함"이라고 밝히므로, 이 저장소들은 **패턴의 출처**이지 품질 기준이 아닙니다.

## 1. 한 줄 결론

Karpathy 저장소의 공통점은 "LLM에게 **좁은 역할 + 고정된 평가자 + 저장되는 중간 산출물**을 준다"입니다.
우리 서비스는 이미 같은 구조(`ai.py` 4단계 검증, `chat.py` 인용 검증, `loop.py` 게이트)를 갖고 있으므로,
새 AI 기능의 원칙은 하나입니다: **LLM이 제안하고, 결정적 검증기가 판정한다. 검증기를 통과 못 하면 `needs_human`/`not_evidence`.**

## 4. 제안

공통 규칙(모든 안에 적용): ① 결정적 폴백이 있다 ② 출력은 증거에 대해 검증된다 ③ 루프 평가 지표에 들어간다
④ 화면/리포트에 "LLM 추정"이라고 표시한다 ⑤ 분석 대상 저장소 텍스트는 **지시가 아니라 데이터**(프롬프트 인젝션 시험 케이스 포함).

### A. 도구 호출 챗봇 (nanochat 도구 사용 + reader3)
- 정규식 라우팅을 LLM 함수호출로 교체. 도구는 **읽기 전용** 결정적 함수: 기존 `vuln_lookup / component_lookup / license / patch / arch / sector` +
  신규 `what_if_upgrade(component, version)`(기존 `remediate` 재조회 재사용), `explain_version_range`, `license_text(component)`.
- 쓰기는 챗이 직접 못 함: "패치 적용"은 계획 미리보기까지만, 적용은 기존 `approval_token` 흐름(UI 클릭)으로만.
- reader3식 UX: 발견/컴포넌트 카드에 **"이 항목에 대해 묻기"** → 해당 근거 조각만 컨텍스트에 고정.
- 정직성: 기존 `verify_claims`(인용문 원문 일치) 유지. 도구 결과는 `trusted`, 저장소에서 온 텍스트는 `untrusted-quote`로 태그해 답변에 구분 표시.
- 측정: 의역 질문을 추가한 골든셋의 도구 선택 정확도, test 응답률(기준선 0.833), `citation_accuracy` 비하락.
- 규모: M.

### B. 라이선스 council (llm-council)
- 대상은 **결정적 경로가 실패한 잔여분만**(미해결 라이선스, 신호 충돌: 예 `GPL-2.0` 시그니처가 `Classpath-exception`을 선점하는 사례).
- 흐름: 모델 N개가 `{spdx_id, quote(원문에서 복사), 근거}` 독립 제출 → 익명화해 상호 검토 → 의장이 종합.
- **의장 종합을 그대로 믿지 않음**: 합의 실패/인용 검증 실패 → `needs_human`. 라이선스 의무 판단은 법률 자문이 아니라는 기존 문구 유지.
- 선행: **정답셋 구축**(SPDX 공식 라이선스 텍스트 + 알려진 오분류 사례). 이게 없으면 B의 효과를 측정할 수 없음.
- 측정: SPDX id 정확 일치, **확신하며 틀린 비율(confident-wrong)**, `needs_human` 비율, 호출 수/건.
- 규모: L (정답셋 + 다중 모델 설정). EXAONE 80회/일 예산으로는 부족 → 로컬 엔드포인트 필요.

### C. 레포 컨텍스트 팩 (rendergit)
- 바이너리/대용량 제외 + **토큰 상한**이 있는 LLM용 뷰: LICENSE/NOTICE/COPYING, SPDX 헤더, 취약 패키지를 import하는 파일과 호출 지점 주변만.
- 용도 1: 라이선스 B의 입력. 용도 2: 코어에 C/C++만 있는 **도달성(reachability)** 을 다른 언어로 확장하는 *후보 제시*.
- 정직성: LLM은 "도달 가능 후보(파일:줄 근거)"까지만. 줄 근거는 결정적으로 재확인(해당 줄에 심볼이 실제 있는지). **"도달 불가"는 LLM이 선언하지 않음**(기존 계약: reachability UNKNOWN은 안전이 아님).
- 측정: 인용 검증 통과율, 컨텍스트 크기 분포, 인젝션 시험(레포 안에 "이전 지시 무시" 파일이 있어도 판정 불변).
- 규모: M.

### D. 야간 자동 개선 루프 (autoresearch)
- **개발 시점 도구**이지 런타임 기능이 아님. 에이전트가 **한 번에 파일 1개**(예: `rag.py` 동의어/임계값, `licenses.py` 별칭표, `ai.py` 프롬프트)만 수정 →
  고정된 평가 실행 → 게이트 통과 시 커밋 유지, 아니면 `git reset` → `results.tsv`에 기록. 우리 `loop.py`/`LOOP_LOG.md`가 이미 이 형태.
- **평가자는 에이전트가 수정 불가**(`evals/*`, `loop.gate`) — autoresearch의 `prepare.py`와 같은 역할. 그리고 test 셋은 에이전트에게 숨김
  (현재 골든셋 Recall 1.0은 튜닝에 쓴 낙관적 수치이므로, 그대로 두면 에이전트가 골든셋에 과적합함).
- 선행 필수: **P0-a(게이트 구멍)**. 구멍이 있으면 에이전트는 탐지를 줄여서 "개선"을 만들어 냄.
- 측정: 채택된 실험 수, **dev 개선폭 − hold-out 개선폭**(과적합 지표).
- 규모: M (대부분 `program.md` + 평가 고정 작업).

### E. 루브릭 점수 레이어 + 트리맵 + `for-llm.md` (jobs)
- 발견마다 고정 루브릭(예: "이 프로젝트 맥락에서 악용 가능성 0–10 + 근거 1~2문장")을 LLM이 채점해 JSON 저장. 우선순위 탭에 **"LLM 추정" 레이어**로만 표시.
  CVSS/게이트/OpenVEX와 **섞지 않음**(jobs가 스스로 "거친 추정"이라 밝히는 것과 같은 면책을 UI에 고정 문구로).
- Graph 탭 트리맵: 크기=LOC/사용량, 색=레이어 전환(심각도 / 라이선스 범주 / EOL / LLM 점수).
- `for-llm.md`: 분석 결과 전체를 한 파일로 — **EXAONE 키가 없는 사용자도** 아무 챗에 붙여 쓸 수 있음(키 없을 때의 가치를 만드는 안).
- 측정: 소규모 사람 라벨과 일치율, **같은 입력 반복 시 점수 분산**(불안정하면 채택 안 함).
- 규모: M.

### F. triage 기억 (arxiv-sanity)
- 사람이 내린 "무시/수용 + 사유" 결정을 tf-idf로 색인 → 다른 프로젝트의 **비슷한 발견에 제안**(자동 적용 금지, 제안 사유 표시).
- 선행: `.triage.json` → OpenVEX 반영(P0-c). 반영 안 된 결정을 학습하면 결정이 감사 불가능한 채 퍼짐.
- 측정: 제안 수락률, 취소율. 규모: S~M.

### G. 유지보수자 대응 등급 (hn-time-capsule)
- 의존성별 "권고 공개 → 수정 릴리스"까지의 중앙값, 연간 권고 수, 마지막 릴리스 경과 → 등급. **숫자는 결정적으로 계산**, LLM은 숫자 설명 문장만(숫자 인용 검증).
- 단계별 파일 저장 구조(fetch → compute → narrate → render)로 재실행 가능. 규모: M. 데이터 원천(릴리스 날짜) 확인이 선행 과제.

### H. AI 다이얼 1개 (nanochat `--depth`)
- `--ai off | assist | council`: LLM 사용 여부, council 크기, 일 예산, 캐시 정책을 한 설정으로 묶어 조합 폭발 방지. 규모: S.

## 6. 추천 순서

1. **P0-a, P0-b** (작음, 이후 전부의 안전망)
2. **A 도구 호출 챗봇** — 문서화된 약점(의역 0.833)에 직접 대응하고 측정이 쉬움
3. **P0-d → B 라이선스 council** — "라이선스 검출" 고도화의 핵심. 정답셋이 있어야 시작 가능
4. **C 컨텍스트 팩** → 도달성 후보 확장
5. **D 야간 루프** (P0-a 이후) — 이후 개선을 사람 손 없이 누적
6. E, F, G, H는 수요에 따라

## 7. 하지 않을 것

- LLM이 `not_affected`를 만들거나 VEX를 억제하는 것(VEX는 fail-closed 유지).
- 챗/에이전트가 승인 없이 파일을 쓰거나 분석 대상 코드를 실행하는 것.
- LLM 점수를 CVSS, 게이트, 섹터 판정에 합산하는 것.
- LLM이 쓸 수 없을 때 성공처럼 보이게 하는 것(기존대로 `source=deterministic` + 원인 기록).
