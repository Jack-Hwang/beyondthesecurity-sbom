--------------------------------------------------------------------------------
2. 왜 만들었나 — 해결하는 문제
--------------------------------------------------------------------------------

엔지니어가 오픈소스를 스캔해 취약점을 찾고, 패치된 버전으로 올리는 것이 최선의 시나리오입니다.
그런데 현실에는 4단 벽이 있습니다.

  (1) 스캔: 프로젝트 안의 오픈소스 컴포넌트와 취약점을 찾아야 한다.
  (2) 호환성: 패치하면 우리 애플리케이션이 안 돌아갈 수 있다.
  (3) 컴플라이언스: AGPL/GPL v3처럼 "소스 복제"가 금지된 라이선스는 그대로 베낄 수 없다.
  (4) 시간: 그렇다고 새로 짤 시간은 없다. 그래서 AI가 아키텍처와 엔진을 분석해
      명세 기반으로 새 코드를 구현하고, 다이어그램·산출물·요구사항을 실시간으로 보여주며,
      단위/통합 테스트를 통과한 코드만 publish 해야 한다.

BTS-SBOM은 이 4단 전체를 한 제품으로 잇습니다:
스캔(1) -> 패치 제안과 호환 리스크(2) -> 라이선스 판정과 클린룸 재구현(3,4) ->
HITL 승인 체인으로 사람이 최종 승인한 것만 실제 파일에 적용(4).

6. 클린룸 재구현 방법론 (이 프로젝트의 독참성)
--------------------------------------------------------------------------------

문제: AGPL/GPLv3 컴포넌트는 소스를 복제할 수 없다. 대체품이 필요한데 시간이 없다.
원칙: 저작권법상 아이디어/기능/명세는 저작물이 아니다. 공개 인터페이스와 행동 명세에서
      새로 쓰면 독자적 저작물이다. 이 과정을 "측정 가능한 벽"으로 구현했다.

  벽 1 (reader): 원본 소스에서 ast로 공개 시그니처와 docstring(계약)만 추출.
                 함수 몸체는 리더 안에 남고 밖으로 나가지 않는다.
  벽 2 (generator): 생성 프롬프트는 명세 텍스트만 매개변수로 받는다. 원본 소스가
                 프롬프트 함수의 인자 자체가 아니어서 구조적으로 새어나갈 수 없다.
  측정 게이트: 생성 결과와 원본의 라인 shingle 중복도를 매번 측정(문턱 0.05,
                 docstring은 명세 유래라 양쪽에서 제거). 실측 0.0.
  오라클: 생성 코드가 "자기 계약 테스트"만 통과하면 부족하다. 원본 프로젝트의
                 레거시 테스트 스위트를 오라클로 채택해 행동 호환성을 측정한다.
                 2008년대 스위트가 파이썬 3.12에서 크래시 나는 부분은 LEGACY_SHIM으로
                 중화하고, 그 한계는 판정에 정직히 기록한다(예: pty 필요 -> 판정 불가).
  루프: 실패한 오라클 출력은 재시도 프롬프트에 그대로 탑승한다(assertion 줄 단위).
                 mimeparse 0.1.3 실측: 14/29 실패 -> 구조화 피드백 루프로 4/29
                 (독립 실행 2회 동일 재현). 남은 4건은 사례별로 이름을 붙여 기록.
  best-of-N: N회 시도 중 오라클 실패가 가장 적은 후보를 출하한다.
  정직 규칙: 호환 실패는 compatibility_failed로 남는다(verdict를 ok로 덮는 버그는
                 발견 즉시 고쳤다). publish는 verdict가 ok일 때만.

배치 실험(실측): 실제 레거시 OSS 64개 패키지, 151행 데이터셋 — 최신 판정 ok 31 /
호환실패 1(pytz) / 레인 진입 전 스킵 32(파이썬2 시대 문법 등). 진입한 것의 97%가 ok.

7. 품질 게이트와 "정직성" 원칙
--------------------------------------------------------------------------------

이 프로젝트의 설계 원칙은 "모르는 것을 아는 척하지 않는다"입니다. 코드로 강제한 규칙:

  - 증거 + 한계 계약: 모든 분석 결과는 evidence(관측값)와 limitations(못 본 것)를 함께 돌려준다.
  - 스킵은 실패가 아니다, 하지만 실패도 아니다: 테스트 파일이 0개를 실행하면 skip으로
    기록한다(조용한 통과 금지). 단, 셸의 실측 출력("Ran 29 tests")이 정적 추정을 이긴다
    — 실제로 돈 스위트를 "스킵"으로 부르는 회귀를 실측으로 잡아 고쳤다.
  - never invent: 요구사항 번호(AC)는 임의로 만들지 않는다. speclint가 명세<->코드
    양방향 추적(missing/extra = 0)을 게이트로 검사한다.
  - 미판정은 미판정: KEV/EUVD를 연동하지 않았으면 취약점 악용 여부는 "미판정"으로 남는다.
  - 문서 게이트: doclint(모든 공개 함수 docstring 존재)·check_md_links(문서 링크 유효)·
    speclint 3종이 테스트로 돈다.
  - 버전 단일 출처: pyproject 2종 + _version.py + CHANGELOG 헤드 + README 샘플이
    하나의 테스트로 전부 일치하는지 검사한다(이 릴리스 0.6.1도 같은 게이트로 검증).

10. 실행 방법 (5분 데모 포함)
--------------------------------------------------------------------------------

  설치/실행 (런타임 의존성 0이라 파이썬 3.11+면 바로):
      python -m bts_sbom_app.server --port 8800 --llm-config evidence/.llm_config.json
      -> http://127.0.0.1:8800  (LLM 없이도 스캔/SBOM/리포트는 전부 동작)

  CLI:
      python -m bts_sbom scan <경로>              # 스캔 + SBOM + 취약점 + 라이선스
      python -m bts_sbom --version                # 0.6.1
      python -m bts_sbom_app.evals_top10          # 챗 품질 TOP-10 스코어카드

  5분 데모 시나리오:
      (1) Scan 탭에서 데모 프로젝트 스캔 -> SBOM/취약점/라이선스 실시간 진행률
      (2) 하단 dock에서 "demo의 취약점을 요약해줘" -> 챗봇이 도구 호출로 답변(SSE 카드)
      (3) 🧬 Clean-Room 탭: 레거시 컴포넌트 명세 -> 생성 -> 카피 게이트 -> 오라클 스트립
      (4) 🚨 사고 대응 탭: 접수 -> SLA 카드 -> IoC 등록 -> 초동보고서 생성
      (5) CRA 탭: readiness 체크 + 부록 J 대장 확인

  Docker/배포:
      docker build -> Trivy CRITICAL 0 게이트 -> ACR push -> Container Apps 배포
      (deploy/azure/ 의 yaml, MI 풀, Easy Auth 설정 포함)
