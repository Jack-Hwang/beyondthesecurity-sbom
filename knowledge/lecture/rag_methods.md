# RAG 방법론 — 청킹·검색·생성·그라운딩

baseline: 500자 청크/50자 오버랩, BM25+TF-IDF를 RRF(k=60)로 융합, verbatim-substring 인용, found=false 처리. 아래는 이 위에 얹을 수 있는 기법만 다룬다. 실패 원인 분류(어휘불일치/고유명사·숫자/중간손실/근거없음) [2주차_3차시_HybridSearch_고급RAG.pdf p.5]가 처방 선택의 전제이므로, 각 기법 적용 전에 먼저 실패 질의를 이 4유형으로 태깅할 것을 권한다.

## 1. 계층(parent-child) 청킹

문서를 조항·섹션 단위 parent(예: 1200자)로 나누고 그 안에서 더 작은 child(예: 300자, 오버랩 포함)로 재분할한다. 검색은 child로 정밀하게, 생성 컨텍스트에는 child가 속한 parent 전체를 주입해 문맥을 보존한다. 메타데이터(문서명·조항·발행일)는 child가 parent로부터 상속하고, child를 모두 이으면 parent 원문이 정확히 복원돼야 한다 [동 PDF p.10, p.24].

### BTS-SBOM 적용
라이선스 전문처럼 조항 구조가 뚜렷한 문서에 parent=조항 전체, child=500자(기존 청크 크기 유지)로 2단 청킹을 추가한다. 측정값: 평면 500자 청킹 대비 Recall@5(child 인덱스 기준)와 인용 정확도(parent 주입 기준)를 골든셋에서 Before/After 비교.

## 2. 쿼리 변환·메타데이터 필터

검색 전 질의 가공 3가지: 쿼리 재작성(구어→문서 표현), 메타데이터 필터(날짜·지역으로 후보를 먼저 좁힘), 멀티쿼리(관점이 다른 질의 여러 개로 재현율 확보). 실습 가이드는 "재작성→필터→리랭킹을 한 번에 하나씩 적용하고 매번 재평가해 기여도를 분리하라"고 명시한다 [동 PDF p.11; 2주차_실습_프롬프트.md S4].

### BTS-SBOM 적용
질의 전처리에 "쿼리 정규화"(CVE 번호·패키지명 정규식 정규화)를 추가한다. 측정값: 적용 전/후 Recall@5 delta를 개별 측정 — "한 변수만 바꿔 측정"은 baseline의 loop engineering 절차와 동일하므로 회귀 게이트 인프라를 그대로 재사용한다. 메타데이터 필터(OSI 승인 여부, CVSS 심각도)는 인덱스 스키마에 필드 추가가 선행돼야 함을 명시.

## 3. 리랭킹

RRF 융합 후 상위 N개를 질의-문서 쌍으로 함께 보는 리랭커(매니지드 시맨틱 랭커 또는 로컬 크로스인코더)로 재정렬한다. 효과는 항상 평가셋으로 확인하라고 강조하며, Azure 없는 환경을 위한 "로컬 폴백"(BM25+로컬 임베딩+코드 RRF+로컬 크로스인코더)도 제시된다 [동 PDF p.6; 2주차_실습_프롬프트.md S3-S4].

### BTS-SBOM 적용
외부 크로스인코더는 stdlib-only 제약상 **적용 불가**. 대신 RRF 상위 10개에 한해 TF-IDF 코사인 유사도를 질의-문서 쌍으로 재계산해 2차 정렬하는 "경량 재정렬"은 기존에 쓰는 TF-IDF만으로 가능하다. 측정값: RRF 단독 대비 상위 5개 재정렬 적용 후 Recall@5/MRR delta(회귀 게이트로 자동 평가).

## 4. 검색 지표 vs 생성 지표 분리

검색은 Recall@k·MRR·nDCG@k, 생성은 근거성·관련성·인용 정확도로 **따로** 측정해야 오답이 검색 실패인지 생성 실패인지 가릴 수 있다. 진단 매트릭스: 검색↑·근거성↓=생성 문제, 검색↓·근거성↑=엉뚱한 근거에 충실(검색 개선 우선) [동 PDF p.15; 별첨_AI에이전트_답변품질_평가지표·방법론_TOP10.pdf p.10-11].

### BTS-SBOM 적용
baseline에 nDCG@5를 추가한다(gold 문서가 이진 관련도라 외부 라이브러리 불필요). baseline의 "verbatim-substring 인용"을 코드로 계산되는 근거성 프록시로 명시하고, 평가 리포트에 검색 지표/생성 지표를 별도 열로 분리 출력해 위 진단 매트릭스를 바로 적용할 수 있게 한다.

## 5. 툴 출력 트림(trim)

검색 결과 원본의 수십 개 필드 중 모델 컨텍스트에는 필요한 몇 개만 추려 넣는다. 트림은 "표시 레이어"가 아니라 "툴 래퍼" 안에서 하고 버린 필드는 trim 로그에 남긴다. 인덱스 스키마가 안정적이면 결정적 필드 필터가 가장 싸다(모델 호출 추가 없음) [동 PDF p.21-22].

### BTS-SBOM 적용
검색 결과를 EXAONE 프롬프트에 넣기 전 `KEEP=[chunk_id, doc_title, article, published, content]` 화이트리스트를 적용하고 버린 필드를 로그에 남긴다. 측정값: 적용 전/후 평균 프롬프트 토큰 수 — 하루 100회 한도에서는 "프롬프트가 한도를 넘겨 호출이 실패하는 빈도"가 더 중요한 지표다.

## 6. 출처 보존·상충 처리

모든 주장(claim)에 인용문·출처·날짜를 붙이고 근거 부족 시 `found=false`. 두 출처가 다른 수치를 말하면 **평균·임의 선택 금지**, 양쪽 값+출처+날짜를 모두 `conflicts`에 담고 해결 규칙(`prefer_newer`/`prefer_authoritative`/`escalate`)을 적용해도 원래 두 값은 로그에 유지한다. 인용 검증은 claim이 가리키는 `chunk_id`가 **이번 검색 결과에 실재**하는지까지 포인터를 따라가며 코드로 확인한다(답변 텍스트만 읽어서는 못 잡음) [동 PDF p.12, p.23, p.25-26].

### BTS-SBOM 적용
(a) baseline의 verbatim-substring 인용 검증에 "chunk_id 실재 검사"를 추가해 "검색되지 않은 근거를 그럴듯하게 인용"하는 실패를 잡는다. 측정값: 골든셋 중 실재하지 않는 chunk_id 인용 건수(목표 0). (b) 라이선스/취약점 정보원이 둘 이상일 때를 위해 `conflicts` 필드와 `conflict_log.jsonl`을 신설한다. 측정값: 상충 테스트 케이스에서 양쪽이 모두 보고되는 비율 100%.

## 7. 툴 설명 설계 5요소

LLM은 툴 이름이 아니라 설명을 읽고 고른다. 설명에 담을 5요소: 하는 일·반환 / 쓸 때 / 쓰지 않을 때(제외 조항) / 입력 힌트 / 출력·오류 신호. 오라우팅의 첫 처방은 이름 변경이 아니라 설명 보강 [동 PDF p.14, 18-19].

### BTS-SBOM 적용
RAG 검색 함수가 2개 이상(예: 라이선스 조회 + 취약점 조회)으로 늘어날 때 docstring을 5요소 템플릿으로 통일한다. 측정값: 긍정/부정 라우팅 테스트 통과율. 현재 단일 함수뿐이면 **적용 보류**.
