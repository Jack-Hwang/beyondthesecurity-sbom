# SDD·요구사항 분석 방법론

원전: 1주차_3차시_요구사항분석_주제선정.pdf, adv-lab.zip의 `ref-project/sdd/`(디렉터리 실물), 과제가이드.zip 채점 루브릭. BTS-SBOM는 이미 "모든 AC가 측정 가능한 숫자를 가진 SDD/EARS 명세"를 전제하므로, 여기서는 명세 구조·품질을 끌어올리는 기법만 추린다.

## 1. EARS 5패턴 + 요구 분류 코드

Ubiquitous(shall)/Event-driven(When)/State-driven(While)/Optional(Where)/Unwanted(If…then) 5패턴. lint 기준은 "패턴 키워드+shall+측정 수치" 3요소 — 수치 없는 문장은 아직 AC가 아니다. 요구는 SFR(기능)/DAR(데이터)/PER(성능)/SIR(인터페이스)/SECR(보안)/CONR(제약) 6개 분류 코드로 나눠 SDD 정본의 해당 섹션에 배치한다 [1주차_3차시_요구사항분석_주제선정.pdf p.5, p.7].

### BTS-SBOM 적용
전체 AC 문장이 5패턴 키워드를 포함하는지, `shall` 뒤에 비교 연산자+숫자가 있는지를 정규식으로 검사하는 `ears_lint.py`를 추가한다. 측정값: 숫자 없이 통과된 AC 건수(목표 0), State-driven(장애 상태 요구, 예: "While OSV API 장애 중, 마지막 캐시 결과를 표시") 패턴 보유 여부. 6분류 코드로 기존 문서를 재태깅해 빈 분류(특히 DAR·SECR)가 있는지도 점검.

## 2. SDD 10섹션 정본 + todos 5섹션

`01_planning/`은 01_feature~10_test 10개 고정 섹션(Placement/Final-Only Rule — 날짜·버전 사본 금지)으로 나뉜다. `02_plan/<domain>_todos.md`는 5섹션(domain summary/feature items/acceptance criteria/current notes/latest verification)을 모두 갖춰야 "plan"으로 인정된다 [동 PDF p.11-12; adv-lab.zip `ref-project/sdd/` 실물].

### BTS-SBOM 적용
10섹션 스캐폴드(특히 `10_test`·`09_security`)가 비어 있지 않은지, todos에 5섹션이 모두 있는지 구조 검사 스크립트로 린트한다. 측정값: 비어 있는 섹션 수, todos 5섹션 완비 여부(불리언). 날짜 붙은 사본(`_v2_FINAL` 류)이 없는지도 점검.

## 3. 명시적 기준 테스트 6종

AC 문장이 ①해석테스트(둘 이상으로 읽히는가) ②공백테스트(무엇을 가정해야 하나) ③출력 미리보기 ④범위점검(멈추는 지점) ⑤직접지시('하지 말 것'만 적지 않았는가) ⑥한 지시 한 목표를 통과하는지 점검한다 [동 PDF p.21].

### BTS-SBOM 적용
기존 골든셋 15개 AC를 이 6테스트로 수동 재검토하고 실패 건수를 리포트한다. 측정값: 6테스트를 모두 통과하는 AC 비율. 분기 1회 수동 감사로 운영(자동화 대상 아님).

## 4. 명확화 vs 가정 판단 매트릭스

실패 비용과 가역성 2축: 고비용+쉬운가역="짧게 확인"(핵심 1문항), 고비용+어려운가역="먼저 명확화"(승인 게이트), 저위험+가역="가정하고 진행"(가정을 로그에 명시), 비가역이면 확인 쪽으로 기운다 [동 PDF p.24].

### BTS-SBOM 적용
EXAONE이 생성하는 "제안된 패치"를 (a)되돌리기 쉬운가 (b)실패 비용이 큰가로 2x2 분류해 자동 적용 여부를 정하는 규칙을 4-layer validator 앞단에 추가한다. 측정값: 자동 적용 vs 사람 승인으로 분류된 패치 비율, 승인 없이 적용된 비가역 패치 건수(목표 0).

## 5. 생성자-평가자 반복 정제 루프

생성자(초안 AC)와 평가자(루브릭 기반 구조화 비평, "무엇이 왜 틀렸나")가 번갈아 패스를 돌리며 수렴 기준 또는 반복 상한에서 멈춘다. 남은 가정은 로그에 문서화해 재실행 없이 검토 가능하게 한다 [동 PDF p.25].

### BTS-SBOM 적용
이 패턴은 BTS-SBOM의 loop engineering(골든셋→측정→변수 하나 변경→accept/rollback)과 구조적으로 동일하다 — 차이는 "변수"가 AC 문장 자체라는 점. AC 명세 개선에도 같은 회귀 게이트를 재사용할 수 있다는 점만 기록(신규 인프라 불필요). 측정값: AC 린트 통과율이 반복마다 상승하는지, 반복 상한(예: 3회) 내 수렴하는지.

## 6. ADR 4섹션 + 주제 선정 매트릭스

ADR은 결정/근거/기각 대안/결과 4요소를 고정 섹션으로 요구하고 lint가 4섹션 존재+기각 대안 1개 이상을 검사한다 [1주차_1차시_통합아키텍처설계.pdf p.38]. 주제 선정은 가치×실현가능성/데이터 가용성·라이선스/규제 리스크/기술요소 3개 이상 4기준으로 비교한다 [1주차_3차시 p.15-17].

### BTS-SBOM 적용
BTS-SBOM의 내부 아키텍처 결정(라이선스 호환성 규칙 엔진 선택, 벡터화 방식 선택 등)을 ADR-NNN 4섹션 템플릿으로 남긴다. 측정값: ADR lint(4섹션+기각 대안 ≥1) 통과율. 기각 대안 없는 ADR은 "결정만 있고 왜 다른 안을 버렸는지 없음"으로 감점 대상.

## 7. 참고: 과제 채점 루브릭 가중치

과제가이드.zip 공통 루브릭은 100점을 "수용기준 정의 20·구현게이트통과 40·설계근거 20·문서증빙 20"으로 나눈다. 구현·게이트 비중이 가장 크고, "일부 실패"도 미제출보다 항상 낫다는 운영 원칙이 있다 [과제가이드.zip 과제1_가이드.html].

### BTS-SBOM 적용
**적용 불가: 외부 채점자 없음.** 다만 4분류("AC정의/구현게이트/설계근거/문서증빙")는 BTS-SBOM 각 모듈(SBOM 빌드·라이선스 해석·OSV 스캔·패치 적용·RAG·loop engineering)의 완성도 자가 점검표로 재활용 가능하다. 측정값: 각 모듈이 4분류 중 몇 개에 "증거 있음"을 표시할 수 있는지(0~4).
