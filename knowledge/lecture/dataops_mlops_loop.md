# DataOps/MLOps — 품질 게이트·버전·드리프트·반복 개선 루프

원전: 2주차_1차시_DataOps_MLOps.pdf, 2주차_2차시의 품질보증 부분, adv-lab.zip `w2-1/init` 코드 스텁. BTS-SBOM의 "loop engineering"(골든셋→측정→변수 하나 변경→accept/rollback)과 가장 직접 맞닿는 챕터다.

## 1. 코드·데이터·모델·프롬프트 네 가지가 함께 결정한다

AI 시스템 결과는 코드·데이터·모델·프롬프트 네 가지가 함께 결정하는데, 코드만 Git·CI로 통제되는 경우가 많다. 데이터는 버전·계약 없으면 재현 불가, 프롬프트는 평가셋 없이 배포하면 회귀를 늦게 발견한다(Hidden Technical Debt 논문 인용) [2주차_1차시_DataOps_MLOps.pdf p.5].

### BTS-SBOM 적용
"코드처럼 버전 관리해야 할 것" 3가지를 점검한다: OSV 스캔/라이선스 호환성 규칙, EXAONE 프롬프트 템플릿, RAG 청크·임베딩 인덱스. 측정값: 평가 리포트가 이 3가지의 버전(또는 커밋 해시)을 함께 기록하는지(안 남기면 재현 불가능한 평가).

## 2. MLOps 성숙도 0~2단계 자가진단

Level 0(수동 실행) → Level 1(파이프라인 자동화) → Level 2(PR마다 자동 게이트). 진단은 예/아니오 질문으로 하고, 한 번에 다음 한 단계만 올리는 것이 원칙(비례성) [동 PDF p.7].

### BTS-SBOM 적용
loop engineering 파이프라인을 자가진단한다: "골든셋 평가가 코드 변경마다 자동으로 도는가?" Yes면 Level 2, 수동 실행이면 Level 1. 측정값: 4축(데이터검증/학습평가/프롬프트버전/배포) × Level 0~2 진단표 1장, 가장 낮은 축을 다음 분기 1순위로 고정.

## 3. CI/CD 게이트 설계 — 차단형 vs 비차단형

트리거(PR/main push/야간 schedule)마다 "무엇을 실행하고 실패 시 무엇이 멈추는지"를 먼저 표로 정의한다. PR 트리거는 실패 시 머지를 차단하고, 야간 schedule(회귀 평가 배치)은 실패해도 이슈만 생성한다(배포를 막지 않음) [동 PDF p.10].

### BTS-SBOM 적용
회귀 게이트를 "머지 차단형"(골든셋 Recall@5/MRR delta −0.02 기준)과 "비차단 감시형"(코퍼스 드리프트 — 새 문서 추가 후 기존 OOD 5개가 여전히 found=false인지)으로 명시적으로 분리한다. 측정값: 두 범주가 CI에서 실제로 다른 처리(차단 vs 알림)를 받는지.

## 4. 평가 루프 4지표 + 실행 시점 3종

4지표: 통과율/회귀율(이전에 통과하던 케이스 중 이번에 실패한 비율, **수정 대상만이 아니라 전체 스위트** 포함)/지연/평가당 비용. 실행 시점 3종: 배포 전(PR마다)/평가셋 갱신 후(이전·현재 버전 모두 재실행해 기준선 재보정)/정기 실행(변경 없어도 드리프트 감지) [동 PDF p.18-20].

### BTS-SBOM 적용
baseline의 "delta>=-0.02" 하나를 통과율/회귀율/지연/평가당 EXAONE 호출수 4열로 확장한다("평가당 비용"을 호출수로 치환하면 하루 100회 예산 관리에 직접 쓰인다). 측정값: 골든셋이 바뀔 때 이전 버전으로도 재실행해 기준선 재보정 후보를 만드는 절차 유무.

## 5. 한 번에 한 변수만 바꿔 기여도 분리 (ablation 원칙)

실습 가이드는 RAG 개선을 "재작성→필터→리랭킹" 순서로 하나씩 적용하고 매번 재평가하라고 명시하며, 평가셋에 맞춘 하드코딩(질문 ID별 분기)을 금지한다 [2주차_실습_프롬프트.md S4]. 이는 BTS-SBOM loop engineering의 정의("변수 하나→측정→accept/rollback")와 동일한 원칙이 독립적으로 재확인된 것이다.

### BTS-SBOM 적용(baseline 원칙의 교차 검증)
최근 N회 loop engineering 변경 로그에서 한 사이클에 바뀐 "설정 항목" 개수가 항상 1인지 검사한다(1보다 크면 원칙 위반 건수로 집계) — 신규 인프라가 아니라 기존 로그에 대한 감사 규칙 추가.

## 6. CI 속 LLM 헤드리스 실행 — 부분 적용

CI에서 LLM 호출은 비대화형 플래그가 필수이며 없으면 입력 대기로 잡이 멈춘다. 재실행 시 이전 findings를 프롬프트에 포함해 "신규·미해결만" 보고하게 해 중복을 막는다. 머지 차단은 동기 API, 비차단 야간 회귀는 Batches API(동기 대비 50% 비용, 최대 24시간, `custom_id` 매칭, 멀티턴 툴 호출 미지원)로 구분한다 [2주차_1차시 p.12-15].

### BTS-SBOM 적용
"구조화 출력 강제 + 이전 findings로 중복 제거"는 EXAONE 호출에 그대로 적용 가능하다. 측정값: 재실행 시 중복 보고 비율(목표 0 근접). **Batches API는 적용 불가**(EXAONE은 동기 Chat API만 제공, 배치 작업 API 없음) — 다만 "차단형은 즉시, 비차단형은 느긋하게" 원칙은 3번 항목으로 이미 동기 호출만으로 반영했다.
