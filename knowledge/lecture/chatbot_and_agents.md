# 챗봇·에이전트 아키텍처

원전: 1주차_2차시_컨테이너AI챗봇.pdf(에이전틱 루프·컨텍스트 관리), 2주차_2차시(검증 4계층), 2주차_3차시(멀티 문서 구조 — 출처·툴 설명은 `rag_methods.md`에서 다뤄 중복 생략). 컨테이너 배포·Azure App Service(BTS-SBOM는 단일 프로세스 stdlib 도구)는 제외.

## 1. 종료신호 기반 루프 + 공회전 탐지

루프 종료는 응답 문구나 반복 횟수가 아니라 구조화된 종료 신호(`stop_reason: end_turn`/OpenAI 호환 `finish_reason: stop`)로 판정한다. 반복 상한(`MAX_ITERS`)은 폭주 방지 안전장치일 뿐 주 종료 조건이 아니며, 도달 시 결과를 숨기지 않고 구조화 에러(부분 결과 포함)를 반환한다. 같은 (툴명,인자) 호출 반복이나 직전과 동일한 관찰이 감지되면 상한까지 기다리지 않고 `reason: spinning`으로 즉시 안전 종료한다(호출 키별 카운터+직전 결과 비교만으로 구현) [1주차_2차시_컨테이너AI챗봇.pdf p.7-8, p.21-22].

### BTS-SBOM 적용
EXAONE은 OpenAI 호환이므로 `finish_reason`을 그대로 쓴다. 호출 루프(패치 제안·레거시 분석 등)에 spinning 가드를 추가한다. 측정값: 루프 종료 원인 분포(end_turn/spinning/상한도달) 로그화, 상한도달 비율이 일정 수치(예: 5%) 넘으면 알림 — 하루 100회 EXAONE 예산이 폭주로 소진되는 것을 막는 직접적 가드레일. spinning 가드가 실제로 걸리는지 의도적 반복 유발 테스트 케이스로 확인.

## 2. case facts 블록 — 요약이 뭉개는 값 보존

점진 요약을 반복하면 금액·날짜·번호 같은 정확한 값이 흐려진다. 처방: 요약 대상에서 제외한 별도 `case facts` JSON 블록에 식별자·수치를 원문 그대로 유지하고, 컨텍스트 맨 앞에 배치한다(lost-in-the-middle 대응). 조립 순서는 "facts→요약→최근 N턴 원문". 갱신은 append-only(이력 중요시) 또는 replace-on-conflict, 충돌은 조용히 덮지 않고 양쪽 기록 [동 PDF p.9-10, p.24-25].

### BTS-SBOM 적용
RAG 챗봇이 멀티턴을 지원한다면 CVE 번호·패키지명·버전·SPDX ID를 `case_facts`로 분리한다. 측정값: 10턴 이상 대화 후에도 이전에 언급된 값이 정확히 보존되는지 회귀 테스트 1건 추가(현재 baseline이 단발 질의-응답이면 **적용 보류**).

## 3. 컨텍스트 예산 4층과 실패 모드

컨텍스트는 ①고정 오버헤드(시스템 프롬프트) ②대화 히스토리 ③주입 데이터(검색 결과) ④출력 여유분으로 나뉜다. 실패 모드: 입력 과다로 거부, 생성 중 초과, 강제 잘라내기로 핵심 유실, 컨텍스트 rot(토큰 증가에 따른 주의 희석), lost in the middle [동 PDF p.23].

### BTS-SBOM 적용
프롬프트 빌더에 토큰 수 추정(문자수/4 휴리스틱이면 충분, 외부 의존 불필요)과 출력 여유분 확보를 명시한다. 측정값: 프롬프트가 한도를 넘겨 호출 전 거부된 횟수(목표 0) — `rag_methods.md`의 "툴 출력 트림"과 직접 연결(③주입 데이터 축소).

## 4. 검증 4계층과 재시도 3원칙 (baseline과 교차 검증)

구조화 출력 검증 4층: ①스키마 준수(결정적) ②비즈니스 규칙(값 범위) ③의미 정합(추출값이 원문과 일치하는가) ④교차 필드(관련 필드 간 모순). 재요청 3원칙: 오류를 구체적으로 전달 / 원문 재첨부 / 실패 필드만 교정(전체 재생성 금지). "재시도 유효(형식·구조 오류)"와 "재시도 무효(원문에 정보 없음 — null 유지, 재시도 불필요)"를 구분한다 [2주차_2차시_학습데이터파이프라인.pdf p.25, p.37].

이 4층은 BTS-SBOM 과제 설명의 "4-layer validator(schema, rule, semantic, cross-field)"와 명칭까지 거의 일치한다 — **신규 기법이 아니라 baseline의 교차 검증**으로 기록한다. 강의가 추가하는 것은 표준 오류 객체 `{layer, field, rule, expected, actual}`와 "재시도 유효/무효" 구분 로직이다.

### BTS-SBOM 적용
baseline validator의 오류 출력에 표준 구조를 적용하고, EXAONE 재요청 시 "원문에 없는 정보" 실패는 재시도 없이 즉시 결정적 폴백으로 전환한다. 측정값: 무효 재시도(같은 결과 반복) 비율 — 0에 가깝게 유지하면 EXAONE 예산 낭비를 줄인다.

## 5. 자가검증 필드

추출 결과에 검증용 보조 필드를 함께 받으면 의미 오류를 코드로 잡을 수 있다. 예: `stated_total`(원문 합계)과 `calculated_total`(모델이 합산)을 모두 받아 코드가 대조하고, 불일치 시 모델이 스스로 `conflict_detected=true`로 표시한다. 판단 불가 범주는 "unclear"로 사람 검토 라우팅 [동 PDF p.12].

### BTS-SBOM 적용
EXAONE이 라이선스 호환성/패치 영향도를 요약할 때 참조 근거 조항 수를 스스로 세어 반환(`cited_clause_count`)하게 하고, 코드가 실제 인용 조항 수와 대조한다. 측정값: 불일치 건수(목표 0, 발생 시 사람 검토 라우팅).

## 6. 지시 설계 — 구체성·범위/제약 (프롬프트 엔지니어링)

모호한 지시는 모델이 길이·형식·독자를 임의로 정하게 한다. 범위(Scope)는 포함/제외/가정/경계 4요소로, 제약(Constraints)은 형식/길이/어조/관점으로 인코딩한다. 경쟁하는 목표는 단계별로 나눠 각 단계 출력을 분리한다 [1주차_3차시_요구사항분석_주제선정.pdf p.20-23].

### BTS-SBOM 적용
EXAONE 프롬프트 템플릿마다 범위 4요소를 명시 섹션으로 둔다 — 특히 "제외"(예: "라이선스 재해석은 하지 않는다, 패치 코드 생성만 한다") 누락이 스코프 이탈의 주원인일 가능성이 높다. 측정값: 템플릿 중 범위 4요소를 모두 명시한 비율(문서 감사, 코드 불필요).
