# 부품 사용 형태별 의무 · 수명주기 신호 · 코드 제안 (BTS-SBOM)

**엔지니어링 신호이며 법률 자문이 아닙니다 — 법무 확인이 필요합니다.**

챗봇의 네 가지 도구(license_obligations · legacy_components · migration_plan · propose_code)가 읽는 규칙의 요약.
세부 수치와 전체 조합 목록은 도구 출력과 코드 표를 따른다.

## 사용 형태별 의무 시나리오

사용 형태는 내부 사용 · 바이너리 형태 외부 제공 · 서비스형 네트워크 제공의 세 가지다. 카테고리별 참고 규칙:
카테고리별로 어떤 범위의 소스 제공이 붙는지는 도구의 시나리오 표를 따르고, 미해결 부품은 **모든 시나리오에서
unknown** 으로 남는다 — 절대 "의무 없음"으로 세지 않는다. 호환성 참고 규칙은 이름으로 고정된 5개만 있고,
그 밖의 조합은 규칙 없음(no_rule)이다 — "호환된다"고 단정하는 규칙은 없다. 완화 선택지는 사람 결정(`needs_human`).

## 수명주기 신호 (legacy)

두 신호만 본다: 버전 주기의 **EOL**(오프라인이면 미검증 내장 표 — 출처에 UNVERIFIED 가 남는다)과 **업스트림 수정 부재**
(OSV 에 고침 버전이 없는 상태). 위험 등급은 결정적이고, 근거가 전혀 없으면 unknown — low 로 주지 않는다.
매핑은 5개 시드(django · angular · spring-boot · rails · laravel)뿐이다.

## 이관 물결과 코드 제안

물결 A는 안전한 버전 올림, B는 코드 검토가 필요한 것(major jump · 사이트 과다 · 등급 불명), C는 경로 없음
(replace · accept_risk(VEX+만료일) · pin · monitor). import 사이트 0건은 **영향 없음의 증거가 아니다** —
import 이름이 부품 이름과 다를 수 있다. 코드 제안은 줄 범위 교체만 하고 diff 는 프로그램이 만들며,
적용은 다이제스트 토큰을 가진 CLI 전용이다 — 웹·챗에는 적용 경로가 없고 `tests_run: false` 가 남는다.
