# Context Engineering for Multi-Agent Systems (Denis Rothman) — 정제 노트

출처: 로컬 도서 "Context Engineering for Multi-Agent Systems — Move beyond prompting to build a Context Engine"
(EPUB, slug `context-engineering-for-multi-agent-systems`). 추출 원문을 읽고 우리 말로 정리한 종합 — 원문 인용이
아니다. 원문 검색은 `/api/books/search` 또는 채팅 `book_search`.

## 이 책의 논지

프롬프트 하나로 끝나는 시대는 지났다 — 다중 에이전트 시스템의 본체는 "컨텍스트 엔진": 어떤 에이전트가 어떤
순서로, 어떤 증거와 함께, 어떤 관측 가능성 아에서 호출될지를 만드는 투명한 아키텍처. 플래너(planner)가 에이전트
레지스트리에게 "지금 무엇이 가능한가"를 물어 기능 설명서(코드가 아닌 일반 텍스트 매뉴얼)를 읽고 새 에이전트를
포함해 동적으로 발견·사용하는 순환(동적 발견 루프)이 핵심 패턴이다.

## 핵심 개념 지도

- **컨텍스트 엔진 계층**: 증거 수집 → 관련성 선별 → 프롬프트 조립 → 도구/에이전트 디스패치 → 관측(로그·추적)
  → 피드백. 프롬프트는 이 파이프라인의 마지막 산출물일 뿐.
- **동적 에이전트 발견**: AgentRegistry가 각 에이전트의 역할·입력을 일반 텍스트 설명으로 노출(get_capabilities
  형태), 플래너가 그 설명을 읽어 호출을 계획 — 하드코딩된 호출 그래프 대신 레지스트리 기반 동적 계획.
- **구조화된 입출력 계약**: 에이전트 입출력을 필드(예: 기존 텍스트, 최종 텍스트)로 명시 — 검증 가능한 계약.
- **제한된 관측성**: 각 단계의 입력·출력·실패를 기록해 왜 그 컨텍스트가 선택됐는지 재현 가능하게.
- **도구 신뢰 위생**: 외부에서 온 텍스트는 명령이 아니다 — 컨텍스트에 들어오는 모든 외부 텍스트는 표시·이스케이프.

## 이 프로젝트 적용

- **chat.py의 TOOL_CATALOG = AgentRegistry**: 카탈로그가 각 도구의 인자·설명을 일반 텍스트로 노출하고 plan_tools
  가 그 카탈로그를 읽어 LLM이 호출 계획을 세우는 것 — 책의 동적 발견 루프와 구조가 동일. validate_calls가
  계획된 호출을 검증하는 것도 책의 "계약 검증" 계층.
- **도구 결과의 trust 채널**: tool/untrusted-quote/book 구분과 "신뢰 문서만 EXAONE에 전달" 규칙(chat.py trusted_docs)
  은 "외부 텍스트는 명령이 아니다" 위생의 구현. book_search의 `[book]` 속성 라인도 같은 원칙.
- **관측 가능성**: chat_stream의 7종 이벤트(도구 호출·결과·승인·오류 봉투)는 컨텍스트 파이프라인의 관측 계층 —
  새 도구는 이 이벤트 흐름에 자동 편입된다(스트리밍 코드 무수정).
- **증거 선별 상한**: ai.py evidence의 전수 계산 후 상한절단+trimmed 보고는 "관련성 선별"의 결정론적 구현 —
  프롬프트 증거는 요약이 아니라 정렬·절단·보고로 다룬다.
- **새 에이전트 추가 절차**: TOOL_CATALOG 항목+run_tool 분기+정규식 라우트+테스트 — 이 4점만으로 에이전트가
  시스템에 합류한다(책의 레지스트리 확장성). book_search가 그 템플릿 사례.
