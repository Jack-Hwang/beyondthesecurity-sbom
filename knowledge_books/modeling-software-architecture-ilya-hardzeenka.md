## 이 책의 논지

아키텍처 모델은 그림 자산이 아니라 **소통·검증·결정의 도구**다. C4 모델(컨텍스트·컨테이너·컴포넌트·코드)과
뷰포인트·관점(perspective)으로 구조·행동·트레이드오프를 표현하고, 모델의 저장·버전관리·생성·검증까지
공학적 파이프라인으로 다룬다. Git이 모델에 최적인지조차 질문한다 — Git은 텍스트 파일용이고, draw.io XML diff는
아키텍처 의미를 드러내지 못하며 이진 이미지는 비교 자체가 무의미하다.

## 핵심 개념 지도

- **C4 계층**: 시스템 컨텍스트(외부와의 경계) → 컨테이너(실행 단위·저장소) → 컴포넌트 → 코드. 각 층은 다른
  독자를 가진다(경영진 → 개발자).
- **뷰포인트+관점**: 구조 뷰포인트에 보안·성능·운영 같은 관점을 겹쳐 읽는다 — 하나의 다이어그램이 모든 질문에
  답하지 못한다.
- **모델 저장 정책**: 편집 가능한 시각 소스는 "구체적 필요(자동 출판·검증·공유 요소 재사용·문서 통합)"가 있을
  때만 유지하고, 없으면 더 단순한 산출물이 정답.
- **분산 시스템 모델링**: 파티션 키(순서 필요 메시지는 같은 파티션), 파티션 수(병렬성 vs 쏠림), 컨슈머 재배치,
  커밋 경계 — Kafka 키와 Elasticsearch 라우팅이 다른 규칙을 따를 수 있음을 명시적으로 모델링.
- **모델 검증 자동화**: 모델에서 규칙(순환 금지, 계층 위반 금지)을 기계로 검사하는 흐름.

## 이 프로젝트 적용

- **arch_intel의 다이어그램 정책**: mermaid 렌더 실패 시 소스 텍스트 폴백은 이 책의 "편집 가능한 소스는 필요가
  있을 때만" 원칙의 응용 — 우리의 필요는 "렌더 의존성 없는 정직한 산출물". Git 저장 규칙(텍스트 우선)과 일치.
- **분산 신호 모델링**: 재구현 레거시에서 큐·인덱스·캐시의 파티션/라우팅 결정을 arch_intel 구조 보고의
  설명 필드로 기록 — "왜 이 키로 나뉘는가"에 답이 없으면 검토 항목.
- **뷰별 독자 구분**: 콘솔 화면별 판(git/risk/compliance/…)은 독자별 뷰포인트 분리 관행 — 하나의 판에 모든
  정보를 쏟지 않는다.
- **모델 규칙 검사**: dep-graph 판의 순환·tangle 비율은 "모델에서 규칙을 기계 검사"의 구현 — 새 규칙(예: 계층
  위반)은 같은 자리에 측정으로 추가.
